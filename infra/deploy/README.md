# Запуск и эксплуатация

[Знакомство с проектом](../../README.md) · [Оглавление документации](../../docs/README.md)

Все команды ниже выполняются из корня репозитория, кроме блоков с явным `cd backend`. Локальная сборка содержит PostgreSQL, приватный MinIO, одноразовый init, backend и Nginx с интерфейсом. Наружу опубликован только веб-порт. Init применяет миграции, создаёт бакет при отсутствии и импортирует каталог работ.

## Подготовить локальный запуск

Нужны Node.js/npm, `make`, `curl` и работающий Docker Compose. Python 3.13.15 и uv нужны на хосте только для прямого запуска backend или его тестов; для Compose они устанавливаются в образе.

Подготовьте исходные файлы:

- XLSX-каталог: `artifacts/dataset/Свод*.xlsx`. Импорт рассчитан на структуру исходного каталога; пустая или произвольная таблица не подходит.
- Для гибридного режима: `artifacts/Models/apoce.pt` и `artifacts/Models/kaggle.pt`. Файлы монтируются только для чтения. Контрольные суммы, классы и сопоставления заданы в [манифесте](../../backend/app/data/yolo-manifest.json).

```sh
make up
make status
make check
```

Приложение открывается на `http://127.0.0.1:8096`. Makefile сначала проверяет наличие входных файлов, устанавливает npm-зависимости, собирает интерфейс и контейнеры, затем запускает сервисы и ждёт готовности API. Создание профиля и облачный анализ не входят в `make up`.

Другой порт: `make up PORT=8097`. Для последующих команд указывайте тот же порт и Compose-проект. По умолчанию проект называется `construction-evidence-local`. Makefile выбирает Docker, если команда установлена; иначе обращается к Podman Compose. Другой уже настроенный движок можно указать через `COMPOSE`, например `make up COMPOSE="podman compose"`.

`make down` останавливает контейнеры с сохранением томов. Не добавляйте флаг `--volumes`/`-v`, если нужны сохранённые фотографии и история. Пароли по умолчанию предназначены для локального запуска. Пароль PostgreSQL выберите до создания БД: смена переменной не меняет пароль роли в существующем томе. Для независимой установки используйте отдельный `COMPOSE_PROJECT`, сохранив старые тома.

## Настроить облачный профиль

Без профиля доступны интерфейс и чтение сохранённых данных; запуск анализа отклоняется. Для нового профиля подготовьте `YANDEX_CLOUD_FOLDER_ID` и ключ с правом исполнения foundation models. Ключ передавайте через окружение, не записывайте в репозиторий, историю команд или логи.

Пример скрытого ввода ключа в zsh:

```zsh
read -rs 'YANDEX_AI_STUDIO_API_KEY?Ключ облака: '
export YANDEX_AI_STUDIO_API_KEY
```

Задайте `YANDEX_CLOUD_FOLDER_ID` в том же терминале, затем:

```sh
make profile
```

Команда запускает `evidence-profile` в контейнере backend и выводит UUID профиля. Она сохраняет конфигурацию в БД без пробного запроса к модели. Создание профиля не подтверждает доступность облака или качество распознавания.

Укажите выданный UUID и пересоздайте приложение с этим окружением:

```sh
export OBSERVER_PROFILE_ID='<UUID из make profile>'
make up
make check
```

Профиль фиксирует настройки Мультимодальной модели, инструкции и формат ответа; гибридный профиль также фиксирует манифест детекторов. Секрет в профиль не включается. После изменения этих настроек создайте новый профиль. Точные настройки облачного адаптера находятся в [исходном модуле](../../backend/app/profiles/deepseek.py), гибридные дополнения в [контракте обработки](../../backend/app/profiles/hybrid.py).

Алиас `latest` в адресе облачной модели не закрепляет её веса у провайдера. Сохранённый профиль фиксирует настройки запроса; идентификатор модели, ответ и сведения об использовании сохраняются для последующей проверки.

Для режима без YOLO задайте `export HYBRID_PHOTO_SIGNALS=0` **до** сборки и создания профиля. Затем используйте тот же порядок `make up`, `make profile`, установка UUID, `make up`. В этом режиме проверка наличия весов в Makefile пропускается. Изменение переменной не превращает ранее созданный гибридный профиль в профиль без YOLO: требуется выбрать UUID соответствующего профиля.

Проверка готовности при выбранном гибридном профиле загружает обе YOLO на CPU и проверяет веса и классы. Linux-зависимости CPU зафиксированы в `backend/uv.lock`. Созданный профиль сам по себе не обходит эти проверки. Каждый пользовательский анализ дополнительно требует согласия на облачную обработку выбранных фотографий и контекста.

## Окружение по задачам

| Задача | Переменные и значения |
| --- | --- |
| Локальный Makefile | `PORT=8096`, `COMPOSE_PROJECT=construction-evidence-local`; `COMPOSE` задаёт Compose-команду |
| Пароли контейнеров | `POSTGRES_PASSWORD`, `MINIO_ROOT_PASSWORD`; Makefile задаёт локальные значения по умолчанию. При ручном запуске задайте их сами; пароль БД должен быть URL-safe для строки подключения |
| Веб-порт | `DEPLOY_PORT`; Makefile экспортирует `127.0.0.1:$(PORT)`, ручной Compose использует переданное значение |
| Облачное исполнение | `YANDEX_CLOUD_FOLDER_ID`, `YANDEX_AI_STUDIO_API_KEY`, `OBSERVER_PROFILE_ID` |
| Выбор нового профиля | `HYBRID_PHOTO_SIGNALS=1` для гибридного режима, `0` для режима без YOLO; Makefile и Compose по умолчанию задают `1` |
| Веса при прямом запуске | `YOLO_MODELS_DIR`; внутри Compose путь закреплён как `/app/artifacts/Models` |
| База для прямого backend | `DATABASE_URL`, строка вида `postgresql+psycopg://user:password@host:port/database` |
| Файлы для прямого backend | `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`; приватный S3 обязателен |
| Регион S3 | `S3_REGION`, по умолчанию `us-east-1` |
| Префикс API | `API_ROOT_PATH=/api` за префиксным прокси; пустая строка при прямом обращении к backend |

Compose задаёт параметры подключения к своим PostgreSQL и MinIO. Переменные `DATABASE_URL`, `S3_*` и `API_ROOT_PATH` из окружения хоста не заменяют эти закреплённые значения автоматически. Для другой схемы размещения требуется отдельная конфигурация. SQLite и публичный бакет не поддерживаются.

## Запустить вручную

### Контейнеры без Makefile

Подготовьте те же исходные артефакты. Задайте разные `POSTGRES_PASSWORD` и `MINIO_ROOT_PASSWORD`, затем привяжите веб-порт к loopback. Везде используйте один Compose-проект, чтобы не получить другую БД при создании профиля.

```sh
export DEPLOY_PORT=127.0.0.1:8096
npm --prefix web ci
npm --prefix web run build
docker compose -p construction-evidence-local -f infra/deploy/compose.yaml build
docker compose -p construction-evidence-local -f infra/deploy/compose.yaml up -d
curl --fail http://127.0.0.1:8096/api/health/ready
```

Для создания профиля в этом варианте выполните `docker compose -p construction-evidence-local -f infra/deploy/compose.yaml run --rm backend evidence-profile`. После установки UUID повторите `up -d` с теми же переменными. На первом запуске готовность может появиться не сразу; Makefile содержит ожидание, одиночный `curl` его не заменяет.

### Backend и интерфейс для разработки

Этот путь требует Python 3.13.15, uv, доступных PostgreSQL и приватного S3. Настройте прямые подключения из таблицы выше. Init требует прав создания бакета и миграций БД. Исходный каталог нужен по тому же пути в репозитории.

```sh
uv sync --project backend --extra test
npm --prefix web ci
```

В терминале backend:

```sh
cd backend
uv run python ../infra/deploy/init.py
uv run evidence-profile
```

Перед созданием профиля задайте облачное окружение и нужный `HYBRID_PHOTO_SIGNALS`: при прямом запуске без этой переменной создаётся профиль без YOLO. После установки выданного `OBSERVER_PROFILE_ID` запустите backend:

```sh
uv run uvicorn app.main:app --host 127.0.0.1 --port 58049 --root-path /api
```

В другом терминале из корня репозитория:

```sh
API_PROXY_TARGET=http://127.0.0.1:58049 npm --prefix web run dev -- --port 58149
```

Интерфейс будет на `http://127.0.0.1:58149`, ReDoc на `http://127.0.0.1:58149/api/redoc`. Для backend без префиксного прокси уберите `--root-path /api` и оставьте `API_ROOT_PATH` пустым. Стандартная команда `uv run evidence-service` запускает backend на порту 8000. Для одних миграций из `backend` используется `uv run alembic upgrade head`.

## Доступ и кабинет владельца

Пользовательские API проектов, фотографий и анализов доступны без входа в аккаунт. Приватный S3 не закрывает доступ через приложение. Перед публичным размещением настройте внешний контроль доступа; запуск анализа может расходовать облачную квоту.

Кабинет владельца доступен по `/admin`. Для установки пароля в Compose:

```sh
docker compose -p construction-evidence-local -f infra/deploy/compose.yaml exec backend python -m app.application.admin_password
```

При прямом запуске: из `backend` выполните `uv run python -m app.application.admin_password`. Пароль вводится скрыто, минимум 8 символов. Логин: `gorshenin-nik`. Сессия HttpOnly действует 8 часов; смена пароля завершает прежние сессии. Административные изменения проверяют точный `Origin` и `X-CSRF-Token`.

Для удалённого входа нужен HTTPS. Исключение для loopback относится к прямому backend и локальному dev-прокси. Nginx стандартного Compose обращается из контейнерной сети, поэтому вход владельца через HTTP возвращает `403 https_required` даже при открытии сайта на localhost.

Для HTTPS-размещения настройте TLS-прокси и передачу реальной схемы соединения до backend, а доверие Uvicorn ограничьте адресами своего прокси. Не доверяйте forwarded-заголовкам от произвольного клиента. В [поставляемом Nginx](nginx.conf) `X-Forwarded-Proto` устанавливается из его собственного `$scheme`; один внешний TLS-прокси перед неизменённым HTTP Nginx не решает эту задачу. Готовая TLS-конфигурация в эту Compose-сборку не входит.

## Диагностика и повтор после ошибки

```sh
make status
make logs
make check
docker compose -p construction-evidence-local -f infra/deploy/compose.yaml logs --tail=100 backend init
curl --fail http://127.0.0.1:8096/api/health/live
curl --fail http://127.0.0.1:8096/api/health/ready
```

`live` проверяет доступность HTTP-процесса. `ready` проверяет БД, миграции, приватный S3, восстановление после сбоев и, если профиль задан, конфигурацию исполнителя. Проверка не вызывает облачную модель и не подтверждает точность распознавания. Готовность без профиля означает возможность чтения, а не запуска анализа.

| Симптом или код | Что проверить |
| --- | --- |
| Не прошла сборка | Исходный XLSX, оба файла весов при гибридном режиме, Node.js/npm и доступность Compose |
| `database_migration_mismatch`, `database_gate_failed` | Подключение к БД и выполнение init/миграций |
| `artifact_gate_failed` | Доступность приватного S3, бакет и права доступа |
| `profile_unauthorized`, `profile_runtime_mismatch` | UUID профиля, его разрешение на исполнение и окружение backend |
| `observer_snapshot_invalid` | Облачный ключ, соответствие профиля текущему коду, контрольные суммы весов и классы YOLO |
| `cloud_consent_required` | Согласие на передачу именно выбранных фото и контекста |
| `profile_retired` | Для нового запуска нужен поддерживаемый профиль; старые результаты остаются доступны для чтения |
| `invalid_plan_binding` | Принадлежность проекта, участка и версии плана; время каждого кадра с часовым поясом |
| `https_required`, `invalid_origin`, `invalid_csrf` | HTTPS, доверенный прокси и параметры административного запроса |
| `provider_call_not_replayable` | Наличие уже зарезервированного облачного вызова; повтор такого анализа запрещён |

При потере ответа на загрузку повтор должен сохранять `Idempotency-Key` и исходное тело запроса. Другие данные с тем же ключом отклоняются с `409`. Это защита загрузки от дубликатов.

Перед облачным вызовом сервер сохраняет его резервацию. После таймаута, ошибки транспорта или неполного ответа вызов с неопределённым исходом автоматически не повторяется. Проверяйте сохранённое состояние через `GET /api/runs/{id}`. Не удаляйте резервации ради повтора: это может повторно израсходовать квоту. Повтор неуспешного анализа разрешён только до первой резервации облачного вызова; иначе нужен отдельный осознанный новый запуск.

Исполнитель продлевает временное право обработки и проверяет его перед публикацией. Восстановление после сбоя переводит прерванный анализ в неуспешное состояние с сохранением записанных оснований. История и отдельные исправления человека сохраняются.

## API и проверки разработки

Через Nginx доступны [ReDoc](http://127.0.0.1:8096/api/redoc), [Swagger](http://127.0.0.1:8096/api/docs) и [OpenAPI JSON](http://127.0.0.1:8096/api/openapi.json). При прямом backend используются `/redoc`, `/docs`, `/openapi.json`. Nginx удаляет `/api/` при передаче запроса и задаёт `X-Forwarded-Prefix: /api`.

```sh
uv run --project backend --extra test pytest backend/tests/test_site_analysis.py -q
uv run --project backend --extra test pytest backend/tests/test_deepseek.py backend/tests/test_hybrid.py -q
npm --prefix web test -- --run
npm --prefix web run build
```

Для тестов БД и S3 нужны отдельные `TEST_DATABASE_URL` и `TEST_S3_BUCKET`, отличающиеся от рабочих. Полный backend-набор: `uv run --project backend --extra test pytest backend/tests -q`. Без тестовых ресурсов часть сценариев пропускается; проверяйте итоговый отчёт. Тесты облачного адаптера с подставными ответами не оценивают точность распознавания. Требования к проверке качества описаны [отдельно](../../evaluation/hybrid/README.md).
