# Жизненный цикл анализа

## Состояния и ожидание

Фотоанализ проходит состояния `queued`, `running`, затем завершение или `failed`. Статус и результат хранятся на сервере; переход на другую страницу не отменяет фоновую работу. Проверяйте состояние существующего анализа перед новой отправкой после обрыва связи. Клиент ограничивает ожидание приёма фотоанализа и запроса восстановления 180 секундами, включая чтение JSON. Обработка в фоне может продолжаться дольше.

## Восстановление фотоанализа

После неудачного фотоанализа редактор может восстановить упавший этап в том же анализе. URL и запись истории сохраняются. Успешные облачные ответы и результаты детекторов используются повторно. Сначала сервер полностью перепроверяет сохранённый отклонённый ответ по контракту исходного профиля и текущим валидатором, без обращения к провайдеру. Успешная перепроверка создаёт отдельную квитанцию с `source_call_id`, `validation_revision` и `usage=null`; исходный ответ остаётся неизменным. Если полная проверка не прошла, явная попытка может сделать новый платный вызов только для неуспешного элемента. Неизвестный исход вызова не считается успехом. Автоматических платных повторов нет.

API: `POST /runs/{run_id}/stages/{stage}/retry`, заголовок `Idempotency-Key: <UUID>`, без тела. Ответ 202: `{"run_id":"...","attempt_id":"..."}`. Только owner/editor и только действительно упавший этап; проверяются действующий исходный профиль, согласие и целостность источников. Повтор того же ключа возвращает ту же попытку, включая потерянный ответ. Клиент сохраняет ключ до определённого исхода и ожидает приём запроса вместе с чтением JSON до 180 секунд; это не срок завершения распознавания; загрузка страницы и polling не отправляют POST. `GET /runs/{id}` возвращает `current_attempt_id`, историю `attempts` и `stages[].retryable/retry_cost`. `retry_cost=true` означает, что может понадобиться новый облачный вызов. Конфигурация анализа, исходные файлы, привязка плана и уже зарезервированный контекст оценки (включая историю) не меняются. Все прежние квитанции видны в `ai_evidence`; `effective` отмечает используемые текущей попыткой.

Сбой ответа `status=incomplete, incomplete_details.reason=max_output_tokens` диагностируется как `response_output_truncated`; частичный JSON не принимается. Установленные профили и их точные промпты/хэши сохранены. В новых запросах ограничивается только длина описательных строк в допустимом подмножестве схемы, без сокращения списков объектов и ссылок на доказательства. Лимит токенов не увеличен.

Совместимый старый API `POST /runs/{run_id}/retry` сохраняет прежнее поведение: необязательное тело `{"repeat_processing": true}` (до 1024 байт) явно разрешает полную новую обработку со связанным анализом. Пустое тело или `false` разрешают её лишь до первого облачного вызова. Новый интерфейс использует восстановление этапа.

## Удаление

Владелец может удалить проект целиком, владелец и редактор могут удалить анализ. Сервер блокирует удаление активных заданий; удаление проекта также блокируется при публикации входных данных. Подтверждение в диалоге необратимо.

Запись операции удаления и очистка объектов разделены. Ответ о принятии операции ещё не подтверждает удаление файлов: `cleaning` означает, что очистка продолжается, `completed` подтверждает завершение. Интерфейс проверяет статус; после сбоя используйте «Проверить статус удаления». Фоновая очистка учитывает ссылки на общие объекты и повторяет незавершённую работу. Исчезновение карточки само по себе не доказывает очистку хранилища.
