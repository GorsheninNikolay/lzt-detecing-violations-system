# Project covers in the selected 3D design

Project covers are public presentation images, separate from photographs submitted for analysis. The project list includes a nullable `cover_sha256`. `GET /projects/{id}/cover` serves the current normalized JPEG; `PUT /projects/{id}/cover` accepts `{ "data": "<base64 image>" }` and requires a UUID `Idempotency-Key`. The same key and body return the same operation result after a lost response. The client reads the current project list after a successful response so a later replacement by another visitor is shown accurately.

Anyone who can open the project list can add or replace a cover. The input accepts JPEG, PNG and WEBP up to 5,000,000 source bytes. The backend also enforces an 8 MB request limit and 25 million input pixels, decodes the image, applies orientation, scales within 1600 × 1600, removes metadata and stores a normalized JPEG in private S3. An exact Origin check and a per-visitor limit of 12 cover requests per hour apply. Compose enables trust in the client address header only because its own Nginx overwrites that header and the backend has no published port. A direct backend deployment leaves that proxy trust off.

The project row stores the current cover hash and size. Immutable S3 keys are scoped by project. Replacement commits the new pointer only after S3 verification. Previous and orphaned cover objects enter a durable delayed cleanup queue; cleanup checks the current pointer again before deleting. The running application's PostgreSQL and MinIO volumes must be retained during an update. If the database is unavailable while an S3 write has an ambiguous outcome, a manual audit of the `project-covers/` prefix may still be needed.

In the local demo, covers and project changes are resettable in memory. The two starting projects use distinct existing demonstration photographs. The entrance marquee contains an outlined slot for every unfilled position; projects fill the third visible row first, with their covers behind the cube outline. The project photograph may tilt only as presentation decoration on a fine pointer. Working analysis images and annotation boxes remain stable.

Verification for this integration: 230 frontend Vitest tests and a production build passed; 61 backend project, engagement, startup and single-image regression checks passed against isolated PostgreSQL with a fake S3 client. The 0024 migration upgraded, downgraded on an empty database and upgraded again; downgrade correctly refused a database containing covers. A focused lifecycle smoke confirmed the cover cleanup task starts and stops. Six CLI-driven headless Chromium checks covered project-specific cards, cover replacement, filled cubes, mobile text enlargement and demo reset. These checks establish local behavior. Actual MinIO, deployed Nginx and the public VPS route require separate readback after deployment.

The source XLSX catalog is not in the Git archive used for releases. Preserve and copy the verified catalog asset into a new release before building its backend image; keep the model bind mount and existing PostgreSQL/MinIO volumes. Back up the database before the additive 0024 migration. If covers have been saved, rollback of the schema is intentionally blocked to avoid losing them.
